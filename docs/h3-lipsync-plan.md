# H3 リップシンク(音楽MV向け)実装プラン — 改訂版

2026-08-22 初版 → **2026-08-22 全面改訂**。
mv_studio_V2 の MV 生成でリップシンクを実現するための調査結果と実装方針。

---

## 改訂の理由(旧版からの差分)

旧版は「H3 の packed sequence の音声行を timestep=0 で凍結する機構を**自作する**」計画だった。
その後、以下が判明したため方針を全面的に変えた。

| 項目 | 旧版の前提 | 改訂後(実測で確定) |
|---|---|---|
| H3 のリップシンク | 未確認。自作の音声凍結が必要 | **`ref2va` の音声参照でネイティブに成立**(自作不要) |
| LTX-2.5 a2v | 同じ機構があるので H3 は不要 | **a2v は口を駆動しない**(実視聴+実測で確定)。H3 が本命 |
| 実装作業 | runner.py への機構追加 | **既存 API の活用 + 呼び出し側の設計** |

旧版が「LTX-2.5 の a2v で足りる」として保留になった判断は**誤りだった**。
a2v は音声 latent を正しく凍結するが、**凍結した音声は口を駆動しない**。
LTX-2.5 の映像・音声の結合が弱いため。実 MV(14シーン・90秒)を生成して視聴し、
口と曲が合わないことを確認済み。松尾氏の報告とも一致する。

---

## 機構の解明(2026-08-23、コード調査で確定)

### なぜ LTX-2.5 では口が動かず、H3 では動くのか

構造が違う。**この差が本件の全て。**

| | LTX-2.5 | MiniMax-H3 |
|---|---|---|
| 映像と音声 | 最後まで**別ストリーム** | **1本の packed sequence** |
| 音声→映像の経路 | 各ブロック1本のゲート付き cross-attention の残差加算のみ(`transformer_ltx2.py:781`) | text/video/audio 全行を**1つの self-attention** に通す(`transformer_minimax_h3.py:600-603`, `344-360`) |
| 音声を凍結すると | 口に届かない(実測で確認) | **口が追従する**(実測 +0.583) |

LTX a2v が「音声latentを正しく凍結しているのに口が動かない」のは実装の不備ではなく、
アーキテクチャ上そうなる。H3 に乗り換える理由はここにある。

### 音声凍結の機構は diffusers に既存。ref2va は既にそれを使っている

- `MiniMaxH3LoopSchedulerStep` は **`audio_latents[num_condition_audio_rows:]` にしか書かない**
  ため、先頭 N 行は全ステップを素通りする
  (`diffusers/modular_pipelines/minimax_h3/denoise.py:231-236`)。
  ブロックの description も *"only the generated rows are ever written, so the anchors
  survive the whole loop"* と明記。
- ref2va の参照音声はこの仕組みで、**ノイズを一切加えず t=1.0(クリーン)で条件付け**される
  (`before_denoise.py:1026-1028`、`encoders.py:748-754`)。時間規約は `t = 1 - sigma` で
  **t=1 がクリーン**(`scheduling_minimax_h3.py:22-23`)。
- 行ごとの timestep は `build_row_timesteps()`(`before_denoise.py:1177-1216`)が作り、
  transformer は `adaln_indices = timestep_indices * MODALITY_NUM + token_tags` で
  行ごとに AdaLN 変調を index_select する(`transformer_minimax_h3.py:583-586`)。
  **行ごとに別 timestep はネイティブ仕様。**

**これで段階0 の測定が完全に説明できる**:
参照行(正確・凍結)が口を駆動する → 入力ボーカルと合う(+0.583)。
生成音声行は別に作られる → 波形は違う(0.112)が内容とタイミングは参照に従う(包絡 +0.918)。
尺が余るのは、生成音声行の長さが要求フレーム数で決まり参照とは独立だから。

### 【訂正】hires-fix は音声凍結の前例ではない

旧版で「hires-fix が `audio_denoise=0` 相当を実装済み」と書いたが**誤り**。
hires-fix は音声をアップスケール/再ノイズしないだけで、**音声は両パスとも通常どおり
デノイズされている**。真の前例は ref2va の参照音声行。

### ComfyUI の Audio Drive との差分【旧記述(2026-08-23、実装前)。**用語・技術判断とも文末「`vocal_lock` の由来と audio_lock との違い」が上書きする**。特に「audio_scale 相当の補正が要る」は反証済み】

コミュニティ実装 `ComfyUI-H3-NativeAudioLock`(**71行**、松尾氏の「約80行」と整合)を実コードで確認:

```python
video_latent, target_audio_template = samples.unbind()[:2]
exact_audio_latent = audio_vae.encode(waveform.movedim(1, -1))
locked["samples"]    = NestedTensor((video_latent, exact_audio_latent))
locked["noise_mask"] = NestedTensor((ones_like(video_latent), zeros_like(exact_audio_latent)))
```

**ref2va との違いは1点**: Audio Drive は**生成対象の音声行そのものを差し替える**。
ref2va は**別の参照行を足し、生成音声行は新規に作る**。
出力音声が入力そのものになるのは、ノードが入力 AUDIO を素通しで返し、ワークフローが
`VAEDecodeAudio` を経由せず `CreateVideo` に直結するため(VAE 往復が経路上存在しない)。

**MV では元曲を被せるので、この利点は不要。** 尺の余りもトリムで解決済み。
Audio Drive に残る可能性は「生成音声行も正確な音声にすることで口の精度が上がるか」だけ。

実装するなら diffusers 側の当たりどころは判明している:
`MiniMaxH3PrepareLatentsStep` は `audio_latents` を受け取ると音声ノイズ描画をスキップする
(runner は現在 None を渡しているだけ)。ただし t2va/fl2va は
`num_condition_audio_rows` が **0 でハードコード**されている(`before_denoise.py:371`)ため、
その経路で凍結するにはレイアウトブロックの差し替えが要る。

**注意**: ComfyUI 側には 2026-08-18 マージの修正 `ff6c8a8`(PR #15375)があり、
それ以前は `scale_latent_inpaint` のオーバーライドが無く、音声latentを
`audio_scale = shift/audio_shift = 12.0/3.0 = 4.0` で割り戻さずモデルへ見せていた。
自前で生成音声行を差し替えるなら同等の補正が要る。

### 【重要】`<Audio N>` は公式には「音色の参照」であり、我々の使い方は仕様外

公式系ドキュメントは *"Reference the timbre only; **do not reuse its words**"*、
さらに *"the reference audio must say a **different sentence** than the one you want in
the video"* と明記している。

**それでも実測では言葉ごと転写された**(README の発話検証で文字一致100%、
本件の歌唱で口が入力ボーカルに +0.583 で追従)。しかし**公式に保証された挙動ではない**。
他の曲・他の声で同じ再現性がある保証はなく、複数曲での確認が要る。

## 確定した事実(実測、`minimax-h3/README.md` 1823行〜)

音声参照によるリップシンクの検証結果。**96GB機、768×1344・141フレーム・30steps、
seed 777、総所要 553.9s、ピーク 87.67GB**。

| 検証項目 | 結果 |
|---|---|
| 台詞の内容が音声参照から伝わるか | **成立** — 検出言語 ja (0.964)、文字一致 **100%** |
| リップシンク | **成立** — 口の開閉と音声包絡の相関 **+0.745(ずれ 0ms)** |
| キャラクター一貫性 | 成立(顔・髪型・制服が参照どおり) |
| 音声の 1:1 コピー | **不成立** — 波形相関 0.112、尺 5.22s → 5.88s |

決定的なのは **プロンプトに台詞を1文字も書いていない**こと。
`<Audio 1>` の台詞に口を合わせる、とだけ指示して同じ日本語が出た。
つまり **台詞はテキストエンコーダを経由していない**。LTX とは機構が根本的に違う。

### MV にとって「音声が 1:1 コピーされない」ことは問題にならない

README 自身がこう書いている。

> 元音声をそのまま使いたいなら生成後に差し替える必要がある
> (相関 +0.745 のシンク精度があるので実用的と思われる。**未検証**)

MV では**生成音声を捨てて元曲を被せる**のが元々の運用なので、この制約は無害。
ただし「差し替えても口が合ったままか」は**未検証**であり、最初に確認すべき一点。

### 既知の限界

- **音素レベルの厳密一致ではない。** 口が開いている区間 4.1秒に対し音声区間 1.6秒。
  発話後も口が動く傾向。歌唱シーンはボーカルがほぼ連続するので影響は小さいと予想されるが未検証。
- **尺はモデルが決める。** 音声参照が1つだけなら音声長から自動導出される(141フレーム=5.88秒等)。

## 課題1: FLF は使えるか → **使えるが、リップシンクとは併用できない**

H3 は2つの重みパーティションに分かれ、**別チェックポイント・別エンドポイント**。

| パーティション | エンドポイント | 用途 | transformer |
|---|---|---|---|
| FL2VA | `/api/fl2va` | 先頭/末尾フレーム条件付け(**FLF**) | `transformer` |
| Ref2VA | `/api/ref2va` | 参照(画像9+動画3+音声3)→ **リップシンク** | `transformer_ref` |

`fl2va` は `image` / `last_image` を取るが**音声参照を取らない**。
`ref2va` は参照を取るが**先頭/末尾フレームの指定という概念がない**。
したがって **同一クリップで FLF とリップシンクは両立しない。**

### 代替案: ref2va の「動画参照」で連続性を担保できる可能性

`ref2va` は**動画を最大3本**参照に取れる。前シーンの末尾クリップを動画参照として渡せば、
FLF に近い連続性が得られる可能性がある。**未検証**だが、検証する価値が高い。
これが成立すれば「連続性 or リップシンク」の二者択一を回避できる。

### 当面の使い分け

既存の `is_singing`(ボーカル区間との重なり ≥0.35)がそのまま分岐条件に使える。
これまでの音楽解析・ボーカル分離の作業は無駄にならない。

| シーン | モード | 担保するもの |
|---|---|---|
| 歌唱あり | `ref2va`(キャラ参照画像 + **分離ボーカル**音声) | 口の同期 |
| 歌唱なし | `fl2va`(FLF)または LTX-2.5 | カットの連続性・速度 |

## 課題2: ref2va を使うのか → **使う。ただし音声は「分離ボーカル」を渡す**

既に `music_analysis.py` に demucs(htdemucs)によるボーカル分離が実装済み。
**フルミックス(ボーカル+伴奏)ではなく、分離したボーカルを音声参照にする。**

理由: H3 は音声から発話内容を読み取って口を作る。伴奏が混ざると、
どの成分に口を合わせるべきか曖昧になる。分離ボーカルなら信号が明確。
これは**既存資産がそのまま効く**数少ない設計判断。

**未検証**であり、フルミックスとの A/B を初期に行うこと。

## 課題3: GPU 構成

現状(C-4): GPU0 = RTX PRO 5000 48GB / GPU1 = RTX 4000 SFF Ada 20GB(E4B が 6.77GB 使用、残 13.5GB)。

### ref2va のガードは「TE用GPU の空き」で決まる(誤解しやすい)

`core/runner.py:3458-3459` の実測由来の閾値。**カード容量ではなく、TE ロード後の空き**。

```
_TE_EXTERNAL_MIN_FREE_GB_REF2VA_32B  = 6.5   # 32B TE 使用時
_TE_EXTERNAL_MIN_FREE_GB_REF2VA_PROJ = 4.0   # 投影TE(4B)使用時
```

理由は「2048px 短辺の参照を vision tower に通す活性化」。下回ると **ValueError で明示的に拒否**
される(黙って OOM させない設計)。`t2va` / `fl2va` / `t2i` はこのガードの対象外。

GPU1(20GB)での計算:

| TE 構成 | GPU1 占有 | E4B 併存時の空き | ref2va 判定 |
|---|---|---|---|
| 32B TE(prune) | ~17.4GB | ほぼ無し | **× 不可** |
| 投影TE **NF4** 3.11GB | 3.11GB | **10.1GB** | ○(閾値 4.0GB) |
| 投影TE **bf16** 8.88GB | 8.88GB | 4.35GB | △ 閾値ギリギリ |

### 構成案

| 案 | 構成 | 品質 | t2va 5秒 | GPU1 | ref2va |
|---|---|---|---|---|---|
| **A** | GPU0 単独 `48gb-lowvram`(32B TE) | **近似なし** | ~215s | 空き | ○ |
| B | GPU1=投影TE NF4 + GPU0=transformer | 近似 + NF4 | 速い | 3.11GB(E4B と共存可) | ○ |
| C | E4B を落として GPU1=投影TE bf16 | 近似あり | 速い | 8.88GB | ○ |
| D | `48gb-dual`(GPU1=32B TE) | 近似なし | **44.2s** | 20GB | **× ガードで拒否** |

**最速の D はリップシンクに使えない。** E4B を落としても GPU1 が 20GB では
32B TE ロード後の空きが 6.5GB に届かない。D が使えるのは `fl2va`(非歌唱シーン)のみだが、
そこは LTX-2.5 の方が速いので採用価値は低い。

**ref2va の VRAM は t2va からほとんど増えない。** 16GB 機の実測で
t2va 11.4GB → 音声参照 11.96GB(**+0.56GB**)。よって案A の ref2va は
`48gb-lowvram` の t2va 38.9GB + 約1GB = **~40GB** と推定でき、48GB に収まる見込み(要実測)。

### 投影TE の品質劣化は「NF4」ではなく「投影」が原因(切り分け注意)

README の PSNR 22.64dB / 鮮鋭度 -23% は **TE 実占有 8.88GB = bf16** の投影TE での測定値。
つまり劣化の主因は 32B → 4B + 学習済み線形写像という**近似そのもの**であり、
NF4 量子化はその上に乗る追加要因。「大意は保持し細部は失う」(実例: 32B版にあった
手前の睡蓮の葉が投影版では水面に置き換わった)。

**品質を優先するなら投影TE を使わない案A が正解。** 速度を優先するときだけ B/C を検討する。

なお投影TE の弱点のうち「台詞タグ `<d>` が使えない」点は**本件では無関係**。
README 自身が「台詞を音声参照で入れる → 投影TE のままで使えます」と明記している
(`core/runner.py:1090`)。

### プリセットの現状

`16gb-proj` に **`H3_TE_PROJ` は既に入っている**(`gateway/backends.py:100-112`)。
ただし `H3_LOWVRAM=group` との組み合わせなので、案B/C(GPU1 常駐 + GPU0 transformer)には
そのまま使えない。`overrides` は `H3_` 接頭辞の任意の環境変数を受け付けるため
(`gateway/backends.py:200-205`)、**新規プリセットを足さずに overrides で構成できる**。

投影TE + 音声参照 + turbo の組み合わせは README で**未検証項目として明示**されている(1992行)。

## 課題4: シーン計画への制約 — **ここが最も影響が大きい**

H3 には現行の音楽先行プランと**衝突する制約**がある。

| 制約 | 値 | 現行プランへの影響 |
|---|---|---|
| **最小尺** | **5.0秒** | **3秒・4秒のシーンが作れない** |
| 最大尺 | 15.0秒 | 現行は ≤12秒なので問題なし |
| **fps** | **24 固定** | LTX 側を24fpsに統一済みなので**一致する** |
| フレーム数 | **17n+5** | 0.708秒刻み。**整数秒にならない** |
| 音声参照の最小長 | 5秒未満は 400 エラー | 同上 |
| upscale | **ref2va では非対応** | 高解像度化は別手段が必要 |
| 音声参照は単独不可 | 画像 or 動画の同伴が必須 | キャラ参照画像を必ず添える |

### fps は 24(30 ではない)— 上流の一次情報で確認済み

diffusers 上流のコメントが明示している。

> MiniMax-H3 generates at a **fixed 24 fps**
> (`diffusers/modular_pipelines/minimax_h3/modular_pipeline.py:27`)

> MiniMax-H3's own clock is **24 fps**, so any other rate is resampled onto it by dropping and
> duplicating frames (`references.py:120`)

「30fps」という記憶の出所は `references.py:76` のドキュメント例
`MiniMaxH3VideoReference(frames=frames, fps=30.0)` と思われるが、これは
**参照動画を 30fps で渡す例**であり、H3 側が 24fps へリサンプルする。生成側の fps ではない。
本アプリ側も `core/runner.py:961` で `FPS = 24`。

直近の14シーン構成は 3,5,6,10,7,4,8,4,9,10,5,9,7,3 秒。
**3秒×2、4秒×2 の計4シーンが H3 で生成不可。**

### 対処

1. **歌唱シーンのみ最小5秒を強制する。** 非歌唱シーンは LTX-2.5 に回すので制約外。
   `plan_scenes_from_music()` に「歌唱区間のシーンは最小5秒」という制約を追加する。
2. **17n+5 の端数は生成後にトリムする。** 要求尺を満たす最小の 17n+5 で生成し、
   正確なシーン尺に切り詰める。LTX の 8n+1 で既に +0.04秒/クリップの端数を扱っており、
   同じ考え方の延長。

## 課題5: E4B(音声LLM)は今後も必要か

**リップシンクには不要になる。** ref2va は歌詞をテキストから受け取らない
(プロンプトに台詞を1文字も書かずに文字一致100%が出た、という実測がその証拠)。
したがって E4B の「歌唱のASR」「歌詞と時間軸のアライメント」は、
**口の同期のためには要らなくなる**。

**ただし別の役割が残る。** 「どのシーンでどの歌詞が歌われているか」が分かれば、
その情景を**映像プロンプトの内容**に反映できる(歌詞に合った絵を描かせる)。
これは口の同期とは独立した価値で、以前からの課題でもある。

**判断**: 案A(GPU0 単独)なら GPU1 は空くので **E4B を残しても損はない**。
落とす判断が必要になるのは案C(GPU1 に投影TE bf16 を置く)を選ぶときだけ。
当面は残し、GPU 構成が確定してから見直す。

なお `is_singing` の判定(ボーカル区間との重なり ≥0.35)と音楽先行のシーン分割は
demucs + RMS 包絡 + silencedetect によるもので、**E4B に依存していない**。
E4B を落としてもこれらは動く。

## 段階的な検証計画

ユーザー方針「MVでは画角を小さくして生成速度を早めた試験をする」に沿い、
**小さい画角・少ないシーン**から始める。各段階で止まれるようにする。

H3 のネイティブ解像度は短辺768(`768x768` / `768x1344` / `1344x768`)。
それ未満(例 512×288)も 32の倍数・最小256 なら受け付けるが、
**ネイティブ未満の品質は未検証**。速度優先の試験用と割り切る。

### 段階0 の結果(2026-08-23 実施、**成立**)

条件: `48gb-lowvram` / GPU0 単独 / 768×768 / 30steps / seed 777 / turbo なし。
参照 = キャラ画像1枚 + **demucs 分離ボーカル 6.0秒**(曲の 50.0〜56.0秒)。
**プロンプトに歌詞は1文字も書いていない。**

| 検証項目 | 結果 |
|---|---|
| 歌唱で口が動くか | **成立** — 静区間 vs 大音量区間で口の開き **1.53倍** |
| 口 vs 生成音声 | +0.593(ラグ +0.083s) |
| 生成音声 vs 入力音声の包絡 | **+0.918**(ラグ -0.042s) |
| **口 vs 元の分離ボーカル(トリム後)** | **+0.603(ラグ +0.042s = 1フレーム)** |
| **元曲への差し替え** | **成立**(README が未検証としていた点) |
| ピークVRAM | **42.08GB**(48GB に収まる。推定 ~40GB に対し実測) |
| 所要時間 | 517.4s(denoise 324.9s / decode 14.6s / 平均 11.2s per step) |

README の発話ベースライン +0.745 には届かないが、歌唱で明確に同期している。
差の原因(歌唱の難しさ / 計測指標の粗さ)は切り分けていない。

**運用上の知見2点:**

1. **尺は末尾に付く(引き伸ばしではない)。** 6.0秒の音声 → 158フレーム(17×9+5)= 6.583秒。
   余剰 0.620秒は無音ではなく H3 が勝手に歌い続けた分(RMS は本編の 1.14倍)。
   **先頭から合っている**ので単純トリムでよい。**トリムすると相関が上がる**(0.563 → 0.603)。
2. **音声参照には必ず分離ボーカルを渡す。** フルミックス包絡とボーカル包絡の相関は
   **+0.088** しかなく、伴奏(ドラム等)に支配される。フルミックスを基準に計測すると
   口との相関は +0.171 まで落ちる(計測を誤りやすい罠)。

**計測上の罠(実際に踏んだ)**:
- 口の開き具合を「ROI のNパーセンタイル閾値以下の画素割合」で測ると、**定義上ほぼ常に N%** に
  なり自己正規化して無意味(実測 0.200〜0.209、std 0.0021)。
  **顔全体の輝度中央値 × 0.55 を固定閾値**にすることで機能した(std 0.0173)。
- 映像(6.583s)を入力音声(6.0s)と直接比べていた。H3 は音声を再生成するので
  **「口 vs 生成音声」「生成音声 vs 入力音声」に分解して測る**のが正しい。
- 最良ラグが探索範囲の端に張り付いたら、相関のピークが存在しない徴候(偽の相関)。
- 計測スクリプトと素材は scratchpad の `h3test/`(`measure2.py`)。

**この結果が Audio Drive の要否を変える。** ref2va の音声参照だけで元曲差し替えが成立した以上、
Audio Drive の最大の利点(出力音声が入力そのもの、波形相関 0.998)は
**元曲を被せる MV では不要**。尺の問題もトリムで解決する。
Audio Drive に残る可能性はリップシンク精度そのものの向上(+0.603 → +0.745 相当)。

## `vocal_lock` の由来と audio_lock との違い(確定版、2026-08-26 命名整理)

本節が正。以前の「ComfyUI の Audio Drive との差分」(上記、2026-08-23 の実装前調査)は
**用語・技術判断とも本節が上書きする**。

### 名前の経緯(重要: 後から差が分からなくならないように)

- **出所は ComfyUI の `ComfyUI-H3-NativeAudioLock`(71行)。作者の呼称は "audio lock"。**
  松尾氏の報告(「約80行」)と行数が整合し、これが実装の出発点になった。
- 「**Audio Drive**」は**本プロジェクトが調査中に付けた造語**で、公式でも作者用語でもない。
  実体は「駆動(drive)」ではなく「凍結(lock)」なので、機構を誤って示唆していた。
  当初 doc に「松尾氏の用法を借りた」と書いたが、**その裏付けは記録に無く、誤り**(訂正)。
- **2026-08-26 に `vocal_lock` へ統一**。`lock` = 機構が audio_lock 由来であることを明示、
  `vocal` = 本実装固有の設計判断(駆動源が分離ボーカル)。
  環境変数は `H3_VOCAL_LOCK` / `MV_H3_VOCAL_LOCK`(旧 `*_AUDIO_DRIVE` は警告付き alias)。

### audio_lock と vocal_lock の違い

**核となる凍結機構は同等。改良ではなく移植。** どちらも「生成対象の音声 latent を自前の
音声で置き換え、denoise 中クリーンに固定する」で、意味論(クリーン凍結)まで一致する。
差が出るのは**実装環境**と**使い方**。

| | audio_lock(ComfyUI) | vocal_lock(本実装) |
|---|---|---|
| 凍結の意味論 | クリーン凍結(`scale_latent_inpaint` を `return latent_image` に上書き。マスク領域の実効 timestep も 0) | **同等**(行 timestep=1.0 = H3 のクリーン + 書き込みスライス空) |
| 実装手段 | `noise_mask` 0 のノード(71行) | `num_condition_audio_rows` の拡張。**diffusers 本体は無改変**、runner 側の state 操作3点 |
| `audio_scale = 4.0` | **必要**。sampler が1本で、音声を映像スケジュールへ載せ替えるため | **不要**。diffusers は音声用スケジューラが別実体(shift 3.0)で載せ替え自体が起きない。※こちらが優れているのではなく**環境の差** |
| 駆動源 | フルミックス(曲そのもの) | **分離ボーカル**(本実装固有の設計判断) |
| 出力音声 | 入力素通し(VAE往復なし、相関 0.998)。付け替え不要 | VAE往復相当(相関 0.94〜0.97)。**この点は audio_lock が優る**。ただし完成MVでは原曲を被せるため実害なし |
| 非歌唱シーン | (フルミックス駆動なので該当なし) | **無音で凍結され、幻声・勝手な口パクが消える**(実測 audio_rms 0.19 → 0.0001)。フルミックス駆動では構造的に得られない**機能的な純増** |
| 適用単位 | 単発クリップ | MVパイプライン全体(シーン別ボーカル切り出し → 17n+5 切り上げ → トリム → 連結の尺整合) |
| 適用範囲 | (未確認) | **ref2va 専用**。t2va/fl2va は `num_condition_audio_rows=0` ハードコードのため対象外 |

**要約**: 凍結機構は audio_lock の移植(同等)。改良したのは**使い方**であり、
その中身は「駆動源をボーカルにしたこと(→ 非歌唱の無音化)」と「MVパイプラインへの統合」。
音声忠実度では audio_lock に劣るが、原曲を被せる運用では問題にならない。

### 実測効果

口の開閉と入力ボーカルの相関 0.190 → 0.350、ラグ **−0.208秒 → 0.000秒**(768×448、同一seed)。
MV通しでは連結・トリムの尺バグ2件の修正と合わせて「目視で判別できない」水準。

### 却下した実装案(再検討の際は先にここを読むこと)

- **progressive 版(毎ステップ sigma まで再ノイズ化)**: ComfyUI の実挙動ですらない。
  動画モデル群は `scale_latent_inpaint` を `return latent_image` に上書きしており
  ノイズを載せ直さない。採用しない。
- **`audio_scale = 4.0` 相当の補正を diffusers 側にも入れる**: 上表のとおり不要。
  8/23 の旧記述にあった「同等の補正が要る」は**反証済み**。
