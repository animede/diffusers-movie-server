# リアルタイム動画アプリ 技術メモ(2026-09-01)

「生成しながら再生する」動画アプリを、Minimax-H3-lipsync-mv と同様の
**独立プロジェクト(専用アプリ)**として立ち上げるための技術メモ。
本メモ作成時点で成立条件(生成速度 < 再生速度)は**実測で達成済み**。
エンジンは本リポジトリ(diffusers-movie-server)の ltx2_5 バックエンドを使う。

## 1. 成立根拠(2026-09-01 実測、RTX PRO 6000 Blackwell 96GB)

LTX-2.5 NVFP4 統合(commit 8bb22fd / a8b84cd、プリセット `nvfp4-fast`)により:

| 測定 | 時間(5秒クリップ) | 対リアルタイム |
|---|---|---|
| パイプライン単体(t2v 512×288・8steps・2回目) | 2.6s | **0.52x** |
| gateway 経由 E2E(t2v・upscaleなし・mp4化込み) | 4.4s | **0.88x** |
| V3 実運用(a2v・音声凍結・テスト解像度) | 3.4〜4.6s(中央値3.9s) | **0.78x** |
| 初回クリップ(ウォームアップ込み) | +1〜13s | 初回レイテンシ |

- モデルロード: 8秒(18.7GB checkpoint、CPU変換込み)。常駐 peak ~33GB(upscaleなし)。
- 品質: nf4 同等以上(同一seed目視+laplacian_var 86.8 vs 70.3)。1024×576 の
  upscale 経路も正常(ただしリアルタイム時は使わない、§4)。
- **0.78x = 22% の実時間マージン**。5秒クリップを再生している間に次の5秒クリップが
  約3.9秒で仕上がる計算。バッファ1クリップ分あれば安定再生できる。

## 2. エンジン側の技術資産(実装済み、再実装不要)

- **NVFP4 スタック**: `backends/ltx2_5/app/nvfp4.py`
  - NVFP4Linear(torch._scaled_mm FP4 GEMM + triton 活性化量子化カーネル)
  - ComfyUI 形式単一ファイルのローダ(diffusers 変換関数 + prompt_adaln 12キー
    追加リネーム + F32→bf16 揃え)
  - **checkpoint フォーマットの罠2件(コメントに詳述)**: nibble 順が cuBLAS と逆 /
    weight_scale は事前 swizzle 済み格納(再swizzle厳禁)。層単体検査では検出不能
    (自作 dequant と自作 GEMM が同じ誤解釈で一致する)→ 公式 bf16 重みとの
    全数値照合が必要だった。**新しい量子化 checkpoint を扱うときは必ず
    bf16 リファレンス照合をすること**。
  - probe 群: `backends/ltx2_5/probes/probe_nvfp4_*.py`(GEMM 速度 / swizzle 検証 /
    層単体 / E2E)
- **音声同期の要素技術**(V3/本リポジトリで実証済み):
  - a2v(音声凍結): frozen scheduler hooks で音声 latent を固定し映像のみ denoise。
    リップシンク「ほぼ完璧」(ユーザー評)。
  - **a2v+末尾フレーム(index=-1)**: 音声同期を保ったマッチディゾルブ
    (gateway f4e2d91 / backend e063d2f で2枚目画像を解禁済み)。
  - **連鎖参照(前クリップ最終フレーム→次の1フレーム目)**: V3 の chain 機構で
    実証済み。会場一貫性は3seed再現、「プロンプトが場所を書けばプロンプト優先/
    無指定なら参照引き継ぎ」の法則(mv_studio_V3/docs/h3-chain-reference-probe-
    20260831.md)。
- **gateway**(port 8630): ジョブAPI・アセット転送・プリセット管理。
  リアルタイムアプリは gateway 経由でも、backends/ltx2_5 を直接 import してもよい
  (レイテンシ最優先なら直接、運用の楽さなら gateway)。

## 3. アプリのアーキテクチャ骨子(案)

```
[プロンプト/演出入力] → [セグメントプランナ(LLM任意)]
   → [生成ワーカー(常駐 pipe、クリップN+1を先行生成)]
   → [リングバッファ(1〜2クリップ)]
   → [プレイヤー(ブラウザ: MSE/WebSocket または mpv)]
```

- **パイプライン化が本体**: クリップNを再生中にクリップN+1を生成。0.78x なので
  バッファは1クリップで足りるが、品質ゆらぎ(たまに6秒かかる)対策に2クリップ推奨。
- **クリップ間の連続性**は既存2機構の使い分け:
  - 情景継続: 連鎖参照(前クリップ最終フレームを次の frame-0 アンカーに)
  - 場面転換: 参照なし+プロンプトで新情景(chain probe の法則どおり)
  - 音楽同期モード: a2v で曲をセグメント分割して各クリップに割り当て
    (V3 の start_sec 方式をそのまま流用)
- **初回レイテンシ**: ロード8秒+初回生成~13秒。アプリ起動時に常駐+ダミー生成で
  ウォームアップしておけば、体感は「再生開始まで~4秒」まで詰められる。

## 4. リアルタイム時の構成ルール(実測に基づく)

- **upscale は使わない**(2x latent upscale+refine+diffusion デコーダで+16秒/クリップ。
  リアルタイム成立を即座に壊す)。`LTX25_DECODER` も diffusion ではなく **vae** 相当の
  経路(upscaleなしジョブは元々 VAE デコード)。
- 解像度は 512×288(テスト解像度)起点。上げる場合は生成時間がトークン数に
  ほぼ比例して伸びるので、0.9x を超えない範囲で(640×352 あたりが次の候補、要実測)。
- 8steps(distilled sigmas)固定。steps を削る実験は品質と相談(4steps 蒸留 LoRA が
  LTX に出てくれば更新)。

## 5. 未解決・リスク(着手時に検証すること)

1. **長時間連鎖のドリフト**: V3 は連鎖を最大3回に制限(MV_H3_CHAIN_MAX)。
   リアルタイムは無制限連鎖になるため、Nクリップごとに「アンカー画像へ戻す」
   「プロンプトで場所を再固定する」等のドリフト抑制戦略が必要(未検証)。
2. **クリップ境界の音のつなぎ**: a2v は音声凍結なので曲そのものは連続するが、
   t2v(音声も生成)モードでは境界で音が不連続になる。リアルタイムで音も生成
   したい場合は要設計(V2A 的な後付け、またはクリップ間で音声 latent を持ち越す
   独自機構 — 未実装)。
3. **持続負荷**: 連続生成しっぱなしでの温度・クロック維持は未測定
   (単発ベンチは boost クロック前提の数字)。
4. **mp4 化のストリーミング**: 現在はクリップ完成後に一括 mp4。プレイヤーへ
   渡すだけならフレーム列を直接送る方が速い(ffmpeg パイプ or 生フレーム
   WebSocket)。E2E 4.4s のうち ~0.6s がここ。
5. **さらなる高速化レバー(順に効く見込み)**:
   - 活性化量子化+to_blocked の kernel 融合(現在 Linear 単体 1.9x 止まりの主因)
   - CUDA Graphs / torch.compile(denoise ループの launch overhead 削減)
   - 低解像度→リアルタイム軽量アップスケーラ(spandrel 系、動画対応要調査)

## 6. プロジェクト立ち上げ時の手順メモ

1. 新ディレクトリ(例: `/home/animede/ltx-realtime`)、venv は
   backends/ltx2_5/.venv を共有(torch 2.11+cu130 / diffusers ピン / triton 3.6。
   tpose-server が diffusers-server と venv 共有しているのと同じ流儀)。
2. 最初のマイルストーン: 「プロンプト1本 → 連鎖参照で 30 秒間途切れず再生」の
   CLI/簡易Webプロトタイプ(プランナもUIも後回し、パイプライン化と連続性だけ検証)。
3. GPU 割当: ltx25 常駐(nvfp4-fast、~33GB)前提で GPU0 に同居可能
   (96GB 中、V3/H3 と同時稼働する場合は要調整)。
4. 参考: MiniMax 公式「Fast H3」(8/29発表、Blackwell 約14倍・リアルタイム志向)は
   重み未公開。公開されたら H3 系リアルタイムも射程に入る(upstream-survey-20260831.md
   §4.5)。それまでは LTX-2.5 nvfp4 が唯一の実行可能なリアルタイム経路。
